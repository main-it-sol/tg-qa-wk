### F1 — Stale claim: code paths missing the `backend/` prefix  *(medium)*

Three wiki pages assert that voice-backend files live under `src/virtrav/voice/…`. The actual implementation under `backend/src/virtrav/voice/…` was scaffolded after the wiki was written:

| Page | Line | Current text | Actual path |
|---|---|---|---|

| `concepts/voice-activity-detection.md` | 17 | `` VAD lives in `src/virtrav/voice/vad.py` `` | `backend/src/virtrav/voice/vad.py` |
| `concepts/adapter-pattern-stt-llm-tts.md` | 16 | `` `src/virtrav/voice/adapters.py` `` | `backend/src/virtrav/voice/adapters.py` |

The wiki pages are *faithful to the raw sketch* (`research/raw/articles/voice-backend-sketch.md`), which shows the unprefixed layout — but the sketch has been superseded by reality. Per the lint workflow's "stale claims superseded by newer sources" criterion, the newer source here is the code itself.

**Suggested fix:** prefix all three with `backend/`. Cheap one-line edits. No semantic change.

**Broader implication (not investigated):** Any other claim derived from the sketch — wire-protocol bytes, state-machine transitions, adapter ABC shape — could also have drifted from the code that now exists in `backend/`. This lint did not audit code-against-doc beyond the path issue. Worth a follow-up pass if those details matter for downstream readers.

### F2 — Imprecise prose in voice-activity-detection.md  *(low)*

`concepts/voice-activity-detection.md` line 17 says VAD drives `speech_start` / `speech_end` events "that move [[voice-session-state-machine]] between `LISTENING` and `THINKING`."

This is incomplete:

- `speech_start` also drives `IDLE → LISTENING`.
- `speech_start` during `SPEAKING` is the barge-in trigger (`SPEAKING → LISTENING`).
- Only `speech_end` is single-purpose (`LISTENING → THINKING`).

The state machine diagram in `voice-session-state-machine.md` lines 30–34 has it right; the VAD page's prose simplifies one step too far. Not a direct contradiction since the VAD page doesn't claim exclusivity, but a reader of only the VAD page would miss the barge-in linkage that the same page then explains in its "Interaction with barge-in" section just below.

**Suggested fix:** soften to something like "driving the `speech_start` / `speech_end` events consumed by [[voice-session-state-machine]] (covering, among other transitions, the move from `LISTENING` to `THINKING` on speech end)."

### F3 — `speech_start` / `speech_end` are both internal events and wire frames *(observation, not a defect)*

Not flagged as a finding to fix, but worth being aware of when reading the wiki:

- `voice-wire-protocol.md` lists them as `server → client` text frames (UI cue).
- `voice-activity-detection.md` and `voice-session-state-machine.md` treat them as internal state-machine inputs.

Both are true — the server derives them from VAD, drives the state machine with them, **and** forwards them to the client. No page states this dual role plainly. Low-priority clarification opportunity, not a contradiction.
